Fluid components are **standard custom elements**. Once they're
registered (via `import "@fluid-ds/components/define/button"` or a
`<script src>` tag from a CDN), every framework can render them as
regular HTML.

That said, each framework has a few specifics worth knowing, mostly
around event handling, TypeScript typings, and how the compiler treats
unknown tags. This page collects them.

## See it running

The same admin workflow, including charts, users, dialogs, settings and
brand/theme controls, is built four ways using the same Fluid components.
This is shared functionality, not a certified cross-framework pixel comparison.

- [**Native HTML**](/demos/native/): buildless, import-map + ES modules.
- [**React**](/demos/react/): React 19 + Vite.
- [**Next.js**](/demos/next/): Next.js 15 App Router, static host HTML with client upgrade.
- [**Angular**](/demos/angular/): Angular 20 standalone, with its settings page
  running on a reactive form through `@fluid-ds/angular`.

The [demos gallery](/demos/) also carries the framework-free sample apps
(settings, admin, data table, analytics, booking, sprint board, QR studio),
which is where the expansion packs are shown in context.

The source for all four lives under `apps/admin-*` in the repo and is the
canonical reference for the per-framework patterns documented below.

The repository has seven representative packed consumers: React, Astro, Next.js,
SvelteKit, Vue, Angular, and plain TypeScript/HTML. Each is copied to an isolated
temporary project and installed from the same packed Fluid tarballs that would be
published. A retained pinned Linux replay uses consumer locks, strict peer checks,
offline frozen installs, and source/artifact hashes; all seven pass typecheck,
build, and their Chromium, Firefox, and WebKit runtime contracts against the final
lock. React's exact internal development ranges also make 10/10 initial and 5/5
final raw packs byte-identical.

The rendering boundary matters. React, Vue, Angular, and plain TypeScript/HTML are
client-rendered fixtures, and their negative controls require the production response
to contain no Fluid declarative shadow DOM. Astro, Next.js, and SvelteKit generate
the declarative shadow DOM at build time, then verify delayed registration, hydration, retained server
nodes, and representative properties, events, slots, and form behavior. A separate
packed Next production-server gate passes concurrent request isolation,
private/no-store semantics, and the same three-engine hydration contract. These are
representative integration contracts, not catalog-wide proof, pixel-equivalence
evidence, or deployed hosting-adapter certification. Adapter-backed Astro and
SvelteKit servers plus Angular SSR and Vue/Nuxt SSR remain outside the supported
fixture policy.

The isolation gate rejects compiler paths outside the copied fixture. Runs retain
their consumer locks and tarballs under `quality/evidence/`, including failures. The
pinned replay was verified on Linux with Node 22 and pnpm 9.15.0; it does not claim
macOS, Windows, native Safari, or mobile-browser certification.

```sh
# From the toolchain checkout, with the three Playwright engines installed:
node scripts/check-framework-fixture.mjs @fluid-ds/admin-react --browser --replay
# Replay all seven pinned consumers without registry access:
node scripts/check-framework-pinned-profile.mjs
```

<Aside type="tip">
  Local development uses workspace packages for fast feedback. The framework contract gate installs
  packed Fluid tarballs before typechecking and building, so imports exercised by those fixtures are
  checked at the publish boundary. This does not validate every recipe on this page.
</Aside>

## React

### Setup

Install the generated React integration. Each component subpath registers only
that custom element and exposes a React 19 wrapper with typed properties, refs,
and named custom-event props. The generator reads fourteen source-verified custom
elements manifests (CEMs), covering all 155 registered elements. Of 166 element/event
pairs, 38 have explicit public payload contracts checked against their actual typed
dispatches; 128 deliberately remain `CustomEvent<unknown>`. Application-owned option
data remains `unknown`. Do not interpret every named event prop as a fully typed
payload contract.

The generated-output gate compares exact wrapper and JSX file contents, including
missing and unexpected files. It checks without regenerating first, so stale
output cannot be hidden by a successful export count.

```ts title="src/main.tsx"
import "@fluid-ds/tokens/base.css";
import "@fluid-ds/tokens/light.css";
import "@fluid-ds/icons/register-defaults";
```

### Using the tags

```tsx title="App.tsx"
import { FluidButton } from "@fluid-ds/react/button";

export default function App() {
  return (
    <FluidButton variant="primary" onClick={(e) => console.log("clicked", e)}>
      Save changes
    </FluidButton>
  );
}
```

Per-component imports remain tree-shakable. `@fluid-ds/react` is also available
as a convenience entry when an application intentionally uses many wrappers.

### React 19 vs 18

| Concern                   | React 19                          | React 18                                                  |
| ------------------------- | --------------------------------- | --------------------------------------------------------- |
| Custom-element tags       | Native                            | Native                                                    |
| Custom-element props      | Passed straight through           | Stringified via attributes; non-string props need a `ref` |
| Custom events (`fluid-*`) | Typed props on generated wrappers | Use a `ref` + `addEventListener`                          |

The generated package declares React 19 support. React 18 has no repository
consumer/runtime fixture; this raw-element fallback is an unverified integration
recipe, not a supported-version certification:

```tsx
import { useRef, useEffect } from "react";
import "@fluid-ds/components/define/input";

export function InputWithCustomEvent() {
  const ref = useRef<HTMLElement>(null);

  useEffect(() => {
    const el = ref.current;
    if (!el) return;
    const onFluidChange = (e: Event) => {
      if (e instanceof CustomEvent) console.log(e.detail);
    };
    el.addEventListener("fluid-change", onFluidChange);
    return () => el.removeEventListener("fluid-change", onFluidChange);
  }, []);

  return <fluid-input ref={ref} label="Project name" />;
}
```

### TypeScript and raw custom-element tags

Wrapper types are included automatically. Applications that intentionally use
raw `<fluid-*>` tags can enable the generated React JSX declarations once:

```ts title="src/fluid-ds.d.ts"
import "@fluid-ds/react/jsx";
```

These declarations cover all published elements and expose each element's real
properties and ref type. The core entry covers core elements; expansion packages
have companion entries such as `@fluid-ds/react/jsx/charts`.
They are generated with the wrappers and checked by
the React consumer fixture, so no per-application catch-all is needed.

React 19 raw custom-element listeners preserve the event's exact spelling.
Use `onfluid-change` on a native tag; use `onFluidChange` on the generated
wrapper, whose event mapping is explicit:

```tsx
import { FluidInput } from "@fluid-ds/react/input";

<fluid-input label="Native input" onfluid-change={(event) => console.log(event.detail)} />;
<FluidInput label="Wrapped input" onFluidChange={(event) => console.log(event.detail)} />;
```

Importing the wrapper above registers `fluid-input`. If using only the native
tag, import `@fluid-ds/components/define/input` separately; JSX declarations
alone do not register elements.

## Vue 3

### Setup

```ts title="src/main.ts"
import { createApp } from "vue";
import App from "./App.vue";

import "@fluid-ds/tokens/base.css";
import "@fluid-ds/tokens/light.css";
import "@fluid-ds/icons/register-defaults";
import "@fluid-ds/components/define/button";

createApp(App).mount("#app");
```

Tell the Vue compiler to treat `fluid-*` as native elements (otherwise
it logs a warning every time it sees an unknown tag):

```ts title="vite.config.ts"
import vue from "@vitejs/plugin-vue";

export default {
  plugins: [
    vue({
      template: {
        compilerOptions: {
          isCustomElement: (tag) => tag.startsWith("fluid-")
        }
      }
    })
  ]
};
```

### Using the tags

```vue title="App.vue"
<template>
  <fluid-button variant="primary" @fluid-click="onClick">
    {{ label }}
  </fluid-button>
</template>

<script setup lang="ts">
const label = "Save changes";
function onClick(e: CustomEvent) {
  console.log("clicked", e.detail);
}
</script>
```

### Gotchas

- `.prop` modifier: if a property's name differs from its attribute, use
  `:variant.prop="..."` to set the property directly. Most Fluid
  props mirror an attribute so this is rarely needed.
- Vue's two-way `v-model` does not bind to custom-element properties by
  default, use `:value` + `@fluid-change` instead.

## Angular

### Setup

Add `CUSTOM_ELEMENTS_SCHEMA` so Angular accepts the `fluid-*` tags
without complaining:

```ts title="app.module.ts"
import { CUSTOM_ELEMENTS_SCHEMA, NgModule } from "@angular/core";
// …

@NgModule({
  declarations: [AppComponent],
  imports: [BrowserModule],
  schemas: [CUSTOM_ELEMENTS_SCHEMA],
  bootstrap: [AppComponent]
})
export class AppModule {}
```

Register components and tokens in `main.ts` exactly like the React/Vue
setup above.

### Using the tags

```html title="app.component.html"
<fluid-button variant="primary" (click)="onClick($event)"> Save changes </fluid-button>
```

### Custom events

Angular's `(eventName)` syntax handles any DOM event, including custom
events:

```html
<fluid-input (fluid-change)="onChange($event)" [value]="searchTerm"></fluid-input>
```

Note Angular's template parser is case-sensitive, use `(fluid-change)`
exactly as the event name, not `(fluidChange)`.

### Reactive forms and ngModel

Angular's form APIs bind through a `ControlValueAccessor`, and it only ships
those for native controls, so a custom element normally needs a hand-written
bridge component per control. `@fluid-ds/angular` ships the accessors instead:
install it next to `@fluid-ds/components` and every Fluid form control binds
with `[(ngModel)]`, `formControlName`, or `[formControl]` like a native input.

```bash
npm i @fluid-ds/angular @fluid-ds/components
```

Import `FLUID_FORM_DIRECTIVES` alongside `ReactiveFormsModule` (or `FormsModule`
if you use `ngModel`), then bind as usual:

```ts title="settings.component.ts"
import { Component, CUSTOM_ELEMENTS_SCHEMA } from "@angular/core";
import { FormControl, FormGroup, ReactiveFormsModule } from "@angular/forms";
import { FLUID_FORM_DIRECTIVES } from "@fluid-ds/angular";
import "@fluid-ds/components/define/input";
import "@fluid-ds/components/define/select";
import "@fluid-ds/components/define/rating";
import "@fluid-ds/components/define/switch";

@Component({
  selector: "app-settings",
  imports: [ReactiveFormsModule, FLUID_FORM_DIRECTIVES],
  schemas: [CUSTOM_ELEMENTS_SCHEMA],
  template: `
    <form [formGroup]="form" (ngSubmit)="save()">
      <fluid-input label="Display name" formControlName="name"></fluid-input>
      <fluid-select formControlName="density">
        <fluid-option value="comfortable">Comfortable</fluid-option>
        <fluid-option value="compact">Compact</fluid-option>
      </fluid-select>
      <fluid-rating formControlName="satisfaction"></fluid-rating>
      <fluid-switch formControlName="notifications">Notifications</fluid-switch>
      <fluid-button type="submit">Save</fluid-button>
    </form>
  `
})
export class SettingsComponent {
  form = new FormGroup({
    name: new FormControl("Rene"),
    density: new FormControl("comfortable"),
    satisfaction: new FormControl(4),
    notifications: new FormControl(true)
  });

  save() {
    console.log(this.form.value);
  }
}
```

Two directives cover the catalog, and `FLUID_FORM_DIRECTIVES` is just both of
them in one import:

| Directive                            | Binds through                                           | Elements                                                                                                                                                               |
| ------------------------------------ | ------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `FluidValueAccessorDirective`        | the `value` property, on `fluid-input` / `fluid-change` | input, textarea, number input, masked input, select, typeahead, segmented control, radio group, slider, rating, date picker, time picker, color picker, tag input, OTP |
| `FluidCheckedValueAccessorDirective` | the `checked` property, on `fluid-change`               | checkbox, switch                                                                                                                                                       |

What that buys you, and where the edges are:

- The accessor reads the element's own `value`, so the control's type survives
  the trip. A rating hands the form a number and a tag input hands it an array
  of strings, while the text-like controls hand it a string as they always did.
- A `null` or `undefined` model writes as an empty string, matching Angular's
  own `DefaultValueAccessor`. Initialize numeric controls with a real number.
- `control.disable()` mirrors onto the element's `disabled` property, and blur
  marks the control touched, so validation timing behaves like a native field.
- The directives attach only where a form binding is present, the same
  convention Angular's own accessors use, so unbound `fluid-*` elements carry no
  Angular behavior. You still need `CUSTOM_ELEMENTS_SCHEMA` for the `fluid-*`
  tags that have no form binding on them.
- Compound-value controls (date range picker, range slider) are not covered yet.
  Bind their properties and events directly.
- The package is compiled in Angular's partial-compilation mode, so any Angular
  20+ CLI build links it as part of its normal build.
- Registering the elements stays your own `@fluid-ds/components/define/*`
  side-effect import, exactly as it is without this package.

The [Angular admin portal](/demos/angular/) runs its settings page on this. See
the [Forms guide](/guides/forms/) for how it sits next to the other frameworks'
form libraries.

## Svelte

Svelte renders custom elements directly. Pass the current value and update it from
the component's custom change event. `bind:value` is not valid on a custom-element
tag; Svelte reserves it for native input, textarea, and select elements.

```svelte
<script>
  import { onMount } from "svelte";

  let value = "";
  onMount(() => {
    void import("@fluid-ds/components/define/input");
  });
</script>

<fluid-input value={value} placeholder="Search" on:fluid-change={(event) => {
  value = event.detail.value;
}}></fluid-input>
```

This exact example is compiler-checked with the fixture's installed Svelte 5
compiler, including a regression that rejects `bind:value`. The separate packed
SvelteKit fixture emits build-time static DSD and verifies delayed registration,
hydration, retained server-node identity, and representative properties, events,
slots, and form behavior across three engines. That matrix does not specifically
certify this binding recipe. Client registration in `onMount` upgrades a host, but
only a server renderer can produce its declarative shadow tree.

## SolidJS

There is no SolidJS repository fixture or runtime gate yet. The following is a
documented integration recipe, not a tested support claim.

Solid passes JSX to standard DOM APIs, so custom elements work without
ceremony. Event handlers use lowercase names that match the event:

```tsx
import "@fluid-ds/components/define/button";

export function App() {
  return (
    <fluid-button variant="primary" on:fluid-click={(e) => console.log(e.detail)}>
      Save
    </fluid-button>
  );
}
```

The `on:` namespace prefix tells Solid to attach via `addEventListener`
rather than the property setter, which is what you want for custom
events.

## CDN setup per framework

You can also load the components from a CDN inside a framework app, no
npm install required. This is handy for prototypes, framework
documentation embedded examples, or storybooks.

```html title="index.html, same as a vanilla app"
<link rel="stylesheet" href="https://cdn.jsdelivr.net/npm/@fluid-ds/tokens@latest/dist/base.css" />
<link rel="stylesheet" href="https://cdn.jsdelivr.net/npm/@fluid-ds/tokens@latest/dist/light.css" />

<script
  type="module"
  src="https://cdn.jsdelivr.net/npm/@fluid-ds/icons@latest/dist/register-defaults.js"
></script>
<script
  type="module"
  src="https://cdn.jsdelivr.net/npm/@fluid-ds/components@latest/dist/components/button/define.js"
></script>
```

The framework still owns the rest of the page; it just renders against
elements the browser registered on its own. See
[CDN reference](/getting-started/cdn/) for URL patterns + pinning.
