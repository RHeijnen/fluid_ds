Fluid supports two server-rendering modes. Choose the one that matches your renderer:

1. **HTML hosts with client upgrade**: the server emits tags such as
   `<fluid-button>Save</fluid-button>`. The browser registers and upgrades them.
2. **Declarative shadow DOM (DSD)**: Fluid's server entry renders the component's
   shadow tree into the response. The browser adopts that tree, then Lit hydrates it.

These modes share server-safe component modules, but they are not the same contract.

## The four SSR contracts

| Contract         | What it guarantees                                                                      | Entry point                          |
| ---------------- | --------------------------------------------------------------------------------------- | ------------------------------------ |
| Import safety    | Importing built package and registration modules in Node does not require a browser DOM | Package and `define/*` entries       |
| Registration     | A `define/*` entry associates a tag with its implementation                             | `@fluid-ds/components/define/button` |
| Server rendering | Lit templates produce HTML containing declarative shadow roots                          | `@fluid-ds/components/ssr`           |
| Client hydration | Lit adopts server-rendered shadow roots instead of replacing them                       | `@fluid-ds/components/ssr-client`    |

Import safety alone does not render a shadow tree. Registration alone does not enable
hydration. Use all three relevant entries for DSD rendering.

## Render declarative shadow DOM

The server entry provides an incremental result for streaming and a convenience function
for renderers that need a complete string.

```ts title="server/render-fluid.ts"
import { html } from "lit";
import { renderFluidToString } from "@fluid-ds/components/ssr";

// Load the SSR entry first, then register only the elements used by this route.
await Promise.all([
  import("@fluid-ds/components/define/button"),
  import("@fluid-ds/components/define/input")
]);

export function renderForm() {
  return renderFluidToString(html`
    <form>
      <fluid-input label="Email" name="email"></fluid-input>
      <fluid-button type="submit">Save</fluid-button>
    </form>
  `);
}
```

The result contains `<template shadowrootmode="open">` for each rendered Fluid element.
Treat the returned string as trusted application output. Do not interpolate untrusted raw
HTML into a Lit template.

For a streaming response, use `renderFluid()` and consume its iterable in order. Await a
promise chunk before requesting later output:

```ts
import { renderFluid, type RenderResult } from "@fluid-ds/components/ssr";

async function write(result: RenderResult, response: NodeJS.WritableStream) {
  for (const chunk of result) {
    if (typeof chunk === "string") response.write(chunk);
    else await write(await chunk, response);
  }
}
```

## Hydrate on the client

The hydration support entry must execute before component definitions:

```ts title="client/register-fluid.ts"
import "@fluid-ds/components/ssr-client";
import "@fluid-ds/icons/register-defaults";
import "@fluid-ds/components/define/button";
import "@fluid-ds/components/define/input";
```

Import that module once from the application's client bootstrap. Do not load it once per
component instance.

If a page can become interactive before definitions load, capture its native state
immediately before registration. Await the returned restoration function before reading
form values or enabling application submission logic:

```ts
import { captureFluidFormState } from "@fluid-ds/components/ssr-client";

const form = document.querySelector("form")!;
const restoreFormState = captureFluidFormState(form);
await import("@fluid-ds/components/define/input");
await import("@fluid-ds/components/define/checkbox");
await restoreFormState();
```

The returned function waits for the supported components' first updates, applies their
captured state through public properties, waits for form values and validity to update,
then restores native focus and supported text selection. It does not replay synthetic
`input`, `change`, `fluid-input`, or `fluid-change` events. Calling it again does not
overwrite edits made after restoration.

The verified host-state contract currently covers `fluid-input` and `fluid-checkbox`.
For these controls, displayed values, host properties, validation and `FormData` agree.
Checkbox restoration preserves the configured submission value instead of replacing it
with the inner native checkbox's default `"on"` value. Checkbox reset defaults follow
explicit `checked` and `indeterminate` attribute writes; reflected live-property changes
and user toggles do not redefine those defaults, including after reconnect.

Native `input`, `select` and `textarea` state is traversed through open shadow roots,
including a control or shadow host passed as the root. Non-text inputs do not receive
unsupported selection calls, and file values are never assigned. This does **not** yet
certify host-state reconciliation for composite controls such as `fluid-select`, date
pickers, radio groups or file inputs. A removed control is skipped, not replaced: callers
must retain the server-rendered nodes. The helper is a point-in-time snapshot, not an
autosave mechanism for later edits, navigation, reload or browser autofill.

<Aside type="caution" title="Keep server and client registration aligned">
  A tag rendered with DSD on the server must have the same definition registered in the browser.
  Missing registration leaves static markup; a different version can produce a hydration mismatch.
</Aside>

## Host-only rendering

Frameworks can emit custom-element hosts without invoking Fluid's Lit renderer:

```html
<fluid-button>Save</fluid-button>
```

Registration modules are server-importable, but loading them on the server is unnecessary
in this mode. Register on the client from the framework's browser entry. Until upgrade,
the host has no Fluid shadow tree. If that transition is visible, reserve layout in global
CSS or hide selected elements with `:not(:defined)`:

```css
@layer fluid-fallback {
  fluid-dialog:not(:defined),
  fluid-drawer:not(:defined) {
    visibility: hidden;
  }
}
```

Do not hide an entire page of controls. That replaces a brief upgrade with unavailable
content on slow or failed JavaScript loads.

| Framework          | Verified rendering mode                | Repository contract                                                                      |
| ------------------ | -------------------------------------- | ---------------------------------------------------------------------------------------- |
| React 19 + Vite    | CSR                                    | Packed build plus three-engine wrapper/native runtime contract                           |
| Vue 3 + Vite       | CSR                                    | Packed build plus three-engine properties/events/slots/refs/forms runtime contract       |
| Angular standalone | CSR                                    | Packed build plus three-engine properties/events/slots/refs/forms runtime contract       |
| Plain TS/HTML      | CSR                                    | Packed build plus three-engine native custom-element runtime contract                    |
| Astro              | Build-time static DSD                  | Packed static build, delayed registration/hydration, and retained-node contract          |
| Next.js App Router | Static DSD + local request-time server | Packed static export plus a production-server isolation/cache/hydration contract         |
| SvelteKit          | Build-time static DSD                  | Packed adapter-static output, delayed registration/hydration, and retained-node contract |

The final retained replay passes all seven representative consumers from tarballs
and portable locks using offline frozen installs. CSR fixtures explicitly reject
unexpected DSD; the three static fixtures require it before registration. A separate
packed Next production-server gate makes the contract route dynamic, verifies two
concurrent request identities and private/no-store cache semantics, then passes the
same hydration contract in Chromium, Firefox, and WebKit. It does not certify a
deployed ingress, CDN, edge runtime, or hosting adapter. Adapter-backed Astro and
SvelteKit servers, Angular SSR, Vue/Nuxt SSR, and Remix remain unverified future depth.

The Node gate expands published JavaScript export targets, including wildcard
subpaths, and imports each distinct built file in a separate fresh Node process.
Package roots, registration, locale, animation, icon and React entries are included.
No browser globals or
other Fluid entries are preloaded, so one entry cannot make another accidentally
import-safe. Rendering then uses Lit's separate SSR registry to render all published
elements and rejects a render-tag inventory that disagrees with the catalog.
CSS, JSON, declarations and the tokens package's explicit TypeScript-source export
are classified outside plain-Node JavaScript certification. This checks built
targets, not installed-package export-condition resolution or every bundler.
Eight Node renderer contracts cover escaping, lazy ordered chunks, nested asynchronous
chunks, error propagation, parser-correct native ancestry and interleaved caller
contexts. Their line,
function and branch coverage gate applies only to Fluid's small built `ssr.js`
wrapper, not Lit itself or the component catalog.

<Aside type="note" title="Server language inheritance is request-local">
  `renderFluid()` and `renderFluidToString()` follow `lang` and `dir` on ordinary native ancestors
  as well as on Fluid hosts. The renderer uses the HTML parser's resulting tree, so optional
  `li`/`p` end tags and table foster parenting do not receive lexical-stack guesses. Context is
  bound to each rendered element and remains isolated across interleaved asynchronous requests; no
  process-global current locale is used. Explicit host attributes still take precedence. The
  [localization and RTL guide](/guides/localization/#server-rendering-and-request-isolation)
  distinguishes this request-local element context from the process-global dictionary registry.
</Aside>

The 213-case browser gate registers the 155-element catalog, checks shadow-root presence and catches
page errors, console errors and hydration warnings. Its separate named-form contract checks
actual retained server control nodes, native typing and checkbox changes before hydration,
host values, `FormData`, focus, text selection, validation, reset and subsequent submission.
Input shadow roots delegate native focus in both client rendering and server DSD, so
platform form-validation focus does not depend on the host's JavaScript `focus()` method.
The machine-derived pre-registration matrix covers all 14 applicable
form-associated elements; eight custom-interaction/file surfaces are explicitly
non-applicable to editing before definition.
A negative-control test verifies that replacing a server input fails the identity check.
The empty, hidden catalog fixtures are not per-component post-hydration interaction proof.

Run the browser matrix with `FLUID_BROWSERS=all pnpm test:ssr-browser` after installing the
declared Playwright engines. Local default is Chromium; selecting unsupported engine names
fails configuration. This fixture uses Vite development modules, not packed production
bundles. Every console warning is attached to the test result. Apart from Lit's exact
development-mode notice, warnings, console errors and hydration warnings fail.
Negative controls prove that render-cycle, unknown, altered and hydration warnings
cannot pass this gate. The former 14-component render-cycle exception list has been
deleted after causal component repairs. The audio catalog fixture uses a valid local
WAV instead of exempting invalid-media warnings.

The separate native-form focus matrix uses isolated client-rendered and DSD fixtures for
`fluid-input`, `fluid-checkbox`, `fluid-switch`, `fluid-textarea`, `fluid-number-input`,
`fluid-typeahead`, `fluid-masked-input`, `fluid-select`, `fluid-time-picker` and
`fluid-date-picker`.
Each case exercises native and Fluid submit buttons through both
pointer and keyboard activation, checks that required fields block submission and receive
native focus without browser errors, then submits an actual edited value. DSD cases also
check the server's focus-delegation attribute and retain the original field and submit
button nodes. The four newer composite-control fixtures also check native pointer and
keyboard submission with application-supplied validation errors, preserve those errors
through a language change, clear them, and verify canonical form values and reset.
Select retains its original server-rendered popup and option shadow roots too.
Date-picker retains the original input, dialog, nested calendar host and calendar
shadow root, and verifies ISO form values and date-event payloads.

This covers ten of the sixteen required form controls, not certification of every
required or composite control. The three-control extension passed all 18 client/DSD
cases across Chromium, Firefox and WebKit with normal process exit on 26 August 2026.
The added date-picker slice passes six more client/DSD cases on Linux after
reproducing invalid-focus failures in every engine. The expanded 96-case combined
matrix passes in a pinned Linux container across Chromium, Firefox and WebKit,
with unchanged source and normal shutdown inside the existing five-minute gate.
Historical Windows WebKit teardown
failures remain open; this is not Safari or cross-platform certification. Native
validation focus is separate from pre-hydration state adoption: the latter remains
limited to `fluid-input` and `fluid-checkbox`.

Next.js, Astro and SvelteKit currently run host-only build contracts in CI, not browser DSD
hydration contracts. Their production-runtime certification remains separate work.

## Next.js host-only example

```tsx title="app/fluid-registry.tsx"
"use client";

import "@fluid-ds/components/ssr-client";
import "@fluid-ds/icons/register-defaults";
import "@fluid-ds/components/define/button";
import "@fluid-ds/components/define/input";

export function FluidRegistry() {
  return null;
}
```

```tsx title="app/layout.tsx"
import "@fluid-ds/tokens/base.css";
import "@fluid-ds/tokens/light.css";
import { FluidRegistry } from "./fluid-registry";

export default function RootLayout({ children }: { children: React.ReactNode }) {
  return (
    <html lang="en">
      <body>
        <FluidRegistry />
        {children}
      </body>
    </html>
  );
}
```

This example uses host-only rendering. Importing `ssr-client` is harmless here and lets the
same browser registry hydrate DSD if a server boundary starts producing it later.

## Operational requirements

- Load token CSS in the server-rendered document head so first paint has the correct values.
- Keep server and browser package versions identical.
- Register only the definitions a route or bundle needs when bundle size matters.
- Preserve server-rendered input values before hydration. Browser gates should exercise
  typed values, reloads, and browser autofill behavior.
- Capture `console.error`, unhandled errors, and hydration warnings in end-to-end tests.
- Test both a cold navigation and a client-side navigation.

## Troubleshooting

### `HTMLElement is not defined`

A dependency may be evaluating a browser-only base class, or an old Fluid build may be
installed. For DSD rendering, load the SSR entry before component definitions. The current
Node gate checks cold built imports without preloading the SSR shim, then uses
the shim for a separate rendering phase. Inspect which phase failed before
changing import order or introducing browser globals on the server.

### A declarative shadow root is missing

Confirm that `@fluid-ds/components/ssr` was loaded before the matching `define/*` module and
that the value was rendered through `renderFluid` or `renderFluidToString`.

### The browser replaces server markup

Confirm that `@fluid-ds/components/ssr-client` runs before every Fluid definition and that
server and client resolve the same component version.

### An input loses its value

Distinguish the initial attribute from the live property. Capture user-entered state before
framework rerenders, avoid replacing the host node, and test the exact framework adapter in
a real browser.
